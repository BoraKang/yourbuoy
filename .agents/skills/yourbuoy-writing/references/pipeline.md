# 일일 파이프라인 v1

에이전트가 매일 한 번 돈다. 발굴 → 백로그 적재 → 선별 → 반제품 →
게이트 검사 → 보고까지 자동이고, 사람이 하는 일은 두 가지다. 질문에
답하기, 발행 결정하기.

핵심 경계: 아이디어는 어디서 가져와도 된다. 그러나 니키의 사례가
확보되기 전에는 어떤 글도 반제품이 될 수 없고, 발행 결정은 니키만
한다.

## 운영 데이터의 정본

블로그 아이템과 상태의 정본은 Notion의
[`yourBuoy Blog Pipeline`](https://app.notion.com/p/7f6c99387bea4128a17f16fd8fcd5d5d)
데이터베이스다. 데이터 소스 ID는
`collection://07e0e605-c84d-4150-a8c3-fb2dd0463d67`이다.

- `_meta/backlog.md`는 2026-08-23 이전 데이터를 이관한 레거시 파일이다.
  새 항목이나 상태 변경을 이 파일에 쓰지 않는다.
- 상태 머신의 모든 조회·추가·수정은 Notion DB에서 수행한다.
- Alma의 원문 일기는 VPS의 비공개
  `/root/.openclaw/workspaces/alma/memory/YYYY-MM-DD.md`가 정본이다.
- 주간 씨앗 선별이 Obsidian 동기화본의 `Nicky 원문`만 읽어 후보를 제안한다.
  사용자가 고른 후보만 후속 대화에서 Notion DB에 넣는다. `Alma Note`와
  민감한 사적 내용은 옮기지 않는다.
- Notion에는 일기 원문 전체를 복제하지 않고, 블로그 후보 판단에 필요한
  최소 사실과 원문 날짜만 기록한다.

## 실행 주체와 역할

세 Codex 자동화는 역할을 겹치지 않게 나눈다.

- `yourBuoy 수요 우선 수확 루프`: 월·수·금 공개 수요 후보 제안
- `yourBuoy 주간 씨앗 선별`: 일요일 Obsidian Daily Catch 후보 제안
- `yourBuoy 일일 편집 루프`: 매일 기존 Notion 아이템 편집

예약 실행은 후보·질문·승인 대기 내용을 보고할 뿐 Notion을 수정하지 않는다.
사용자가 해당 Codex 작업에 답한 후속 대화만 승인된 변경을 처리한다. 중복
판정과 상태 변경의 정본은 위 Notion 데이터베이스 하나다.

## 상태 머신

```
                  사례 부족
        씨앗 ──────────────→ 질문중 ──┐
         │                            │ 답변 수신
         │ 사례 충분                   ↓
         └──────────────────────→ 반제품 ←──────┐
                                      │          │
                                게이트 검사       │ FAIL 또는
                                      │          │ 수정 지시
                                    PASS         │
                                      ↓          │
                                    게이트 ───────┘
                                      │
                                  일일 보고
                                      │
                                 니키 결정
                              ↙       ↓       ↘
                            수정     발행      접기
                             ↓        ↓         ↓
                           반제품   PUBLISHED   사망

질문중 30일 무응답 → 사망
씨앗·반제품에서 니키가 접음 → 사망
```

- **씨앗**: 주워온 아이디어. 한 줄 요약 + 출처 + 추정 장르
- **질문중**: 선별됐고 사례 질문 1~3개가 일보에 나가 있음
- **반제품**: 필요한 니키 사례가 확보되어 처음부터 끝까지 작성된 초안.
  사실·경험에 관한 `[확인: ...]`이 0개. 니키의 최종 승인과 문체 편집은
  아직이다. 질문을 거쳤든 안 거쳤든 이 정의를 만족하면 반제품이다
- **게이트**: 아래 게이트 검사를 전부 통과하고 승인 대기 중
- **사망**: 지우지 않고 남긴다. 니키가 다시 언급할 때만 부활한다

승인 거절 시 니키의 지시에 따른다. 수정 요청이면 반제품으로, 폐기면
사망으로.

## 사례 충분 판정 (이 시스템의 심장)

다음 다섯 요소 중 **2개 이상이 니키의 원문에** 존재해야 사례가 있다고
인정한다.

1. 구체적인 상황
2. 실제로 한 행동
3. 당시의 판단이나 생각
4. 결과
5. 이후 바꾼 행동 또는 현재의 판단

2개 미만이면 질문중이다.

2/5는 작성 허가 조건이지 좋은 글의 보증이 아니다. 장르별로 하나씩 더
필요하다.

| 장르 | 추가 필수 |
|---|---|
| 업무팁 | 3(당시의 판단·생각) 또는 5(현재의 판단) 중 1개 |
| 일상 | 추가 조건 없음 |
| 개발기 | 2(실제 행동) 또는 4(결과) 중 1개 |

상황과 행동만 있는 업무팁은 에이전트가 생각을 대신 만들게 된다.
그 순간이 이 표가 막는 지점이다.

그리고 무엇보다:

> **니키가 말한 사실로부터 합리적으로 추론 가능한 내용이라도, 니키의
> 경험·생각·감정으로 서술하지 않는다.**

"강의 준비 너무 오래 걸렸다"는 발언에서 "저는 구조보다 사례를 먼저
보여주는 게 중요하다는 걸 깨달았습니다"를 만들면 안 된다. 앞은 사실이고
뒤는 에이전트의 해석이다. 해석이 그럴듯할수록 위험하다.

## 1. 발굴 (매일, 상한 5개)

| 출처 | 줍는 것 |
|---|---|
| Obsidian `i. Raw/alma/YYYY-MM-DD Daily Catch.md` | Alma에서 동기화된 최근 기록의 `Nicky 원문` |
| 니키와의 대화·메모 | 지나가듯 말한 경험, 반복해서 꺼내는 주제 |
| 진행 중인 프로젝트 | 만들다 막힌 것, 되돌린 결정 (개발기 씨앗) |
| 발행 글의 GSC 쿼리 | 글은 없는데 노출이 잡히는 검색어 |
| Ahrefs | yourbuoy.kr 주제군의 수요 키워드 |

같은 씨앗이 이미 있으면 새로 만들지 않고 출처만 추가한다.

**Daily Catch 규칙**: Daily Catch 안의 Alma Note는 니키 원문이 아니다.
사례 충분 판정에는 니키의 답변 부분만 쓴다. 어제 에이전트가 만든
가설을 오늘 에이전트가 니키의 생각으로 오인하는 것을 막는 규칙이다.

**백로그 항목 스키마** (Notion `yourBuoy Blog Pipeline`):

```markdown
## 037
상태: 씨앗          # 씨앗 | 질문중 | 반제품 | 게이트 | 발행 | 사망
장르: 업무팁
주제: 준비를 덜 했는데 고객 미팅이 더 잘된 이유
출처: Daily Catch 2026-08-21
수집일: 2026-08-22
근거:
- 평소에는 자료를 많이 준비했다 (니키 원문)
- 이번에는 질문 중심으로 진행했다 (니키 원문)
gate_fail:          # 게이트 실패 시에만
질문:               # 질문중일 때만
```

근거에는 니키 원문 사실만 적는다. 에이전트의 해석을 근거에 넣지
않는다.

**외부 검색 데이터 제한**: GSC·Ahrefs만으로 발굴된 씨앗은 선별 대상이
될 수 없다. 니키의 기존 경험·관심사와 연결되는 근거가 대화·메모에서
발견되어야 선별 후보가 된다. 그 전까지는 씨앗으로만 남는다. 이
제한이 자동 SEO 블로그와 yourBuoy를 가르는 경계다.

## 2. 선별 (매일, 최대 1건)

점수제가 아니라 순서다.

1. 최근 7일 안에 니키가 직접 언급한 주제
2. 사례가 이미 원문에 존재하는 것 (판정 기준 위)
3. 검색 수요가 확인된 것
4. 같은 장르 3연속이면 다른 장르 우선

검색 수요가 3순위인 것은 의도다. 수요 → 글 순서가 되면 nitrox가 된다.
여기는 내가 요즘 생각하는 것 → 내 경험이 있는 것 → 그중 사람들이
찾는 것 순서로 간다.

**WIP 제한**: 질문중 3건이 차 있으면 오늘은 선별하지 않는다. 시스템
속도는 에이전트가 아니라 니키의 답변 속도에 맞춘다.

## 3. 반제품 작성

- 사례 충분: 초안을 끝까지 쓴다
- 사례 부족: 질문 1~3개를 만들어 질문중으로. 질문은 일보에 싣는다.
  별도 핑 없음, 재촉 없음

**사례 표현 규칙**: 사례의 사실·행동·판단은 니키 원문에서만 가져온다.
문장은 voice.md에 따라 편집할 수 있으나 의미를 추가·삭제·변형하지
않는다. 원문 복붙이 목적이 아니라 사실 보존이 목적이다.

작성은 SKILL.md 워크플로 ⑤~⑦을 따른다.

## 4. 게이트 검사 (에이전트가 통과시키고, 발행은 니키가 결정)

반제품에 대해 네 묶음을 검사한다. 하나라도 실패하면 반제품 유지하되,
실패 사유를 백로그 항목에 저장한다.

```
gate_fail:
- yourBuoy: 경험보다 일반론 비중이 높음
- Fact: ○○ 수치 출처 확인 필요
```

다음 실행에서 분기한다.

```
Gate FAIL
   ↓
에이전트 혼자 수정 가능한가?
   ├ YES → 수정 → 재검사
   └ NO (니키의 정보가 필요) → 질문중으로 이동
```

이 분기가 없으면 매일 같은 검사와 같은 실패를 반복한다.

**Authenticity**
- 니키가 하지 않은 경험이 추가되지 않았는가
- 니키가 하지 않은 판단·감정이 추가되지 않았는가
- 사례의 구체적 사실이 원재료와 일치하는가

**yourBuoy**
- 실제 경험이 글의 중심에 있는가
- 일반론만 남은 문단이 과도하지 않은가
- 억지로 교훈화하지 않았는가
- 지나치게 반듯한 AI식 구조가 아닌가 (voice.md 최종 테스트)

**Editorial**
- 이 글을 지금 발행할 이유가 있는가
- 독자가 가져갈 것이 있는가 (일상 글은 예외)
- 해당 장르의 사고 흐름을 만족하는가 (genres.md)

**Fact**
- 외부 사실·수치·제품 기능 등 검증 가능한 주장을 확인했는가
- 확인할 수 없는 외부 사실을 단정하지 않았는가

여기에 SKILL.md 발행 게이트의 형식 항목(front matter, slug, 이미지,
nicky-style-check, 원장 기록)을 더해 전부 통과하면 게이트 상태가 된다.

## 5. 측정 알림

- D+30 도래 글: 색인·쿼리 확인 결과 한 줄
- D+90 도래 글: 발행 당시 원장(learning-loop.md)에 기록한 노린 검색어와
  예측값을 실제 결과와 대조한 표를 만들어 판정 요청
- 분기 리뷰 시점: 리뷰 초안 첨부

**원칙 자동 변경 금지**: 성과가 좋아도 에이전트가 voice.md·발행
원칙·장르 규격을 스스로 바꾸지 않는다. 경로는 항상 하나다.
결과 → 관찰 → 가설 → 분기 리뷰 → 니키 판단 → 원칙 변경.
승격 요건은 learning-loop.md L-4를 따른다.

## 6. 일일 보고 (일보가 곧 UI다)

매일 아침 Codex 자동화가 만든 작업에 메시지 하나를 남긴다. 없는 섹션은
생략한다. 니키는 그 작업에 그대로 답장하며, 후속 대화가 Notion 상태 변경과
초안 작업을 처리한다.

UX 원칙 1: **니키가 이 메시지에 답장하는 것만으로 하루치 운영이
끝나야 한다.** 링크를 열게 하는 보고는 실패다. 그래서 승인 대기 글은
일보에 **전문을 싣는다.** 일보가 길어지는 것은 감수한다.

```
yourBuoy 일보 YYYY-MM-DD

[답변 기다림] ← 항상 맨 위
■ (아이템) 질문 1~3개

[승인 기다림]
■ (제목)
────────
본문 전문
────────
→ 발행 / 수정: ○○ / 접기

[오늘 주운 씨앗 N개]
- 한 줄씩

[측정]
- D+30/D+90 도래 항목

[백로그] 씨앗 N / 질문중 N / 반제품 N / 게이트 N
```

### 니키의 입력 문법

자연어면 되지만, 최소한 아래는 해석해서 한 번에 처리한다.

| 입력 예 | 처리 |
|---|---|
| "1번: 내가 실제로 한 건 ○○였어" | 답변을 원재료에 추가 → 반제품 생성 |
| "2번 글 발행" | 명시적 발행 승인 → 게이트 재확인 → _posts 이동, 원장 기록, 커밋 |
| "3번은 접자" | 사망 처리 |
| "이 씨앗은 개발기보다 업무팁 같아" | 백로그 장르 수정 |
| "2번 여기 고쳐서 다시" | 게이트 → 반제품, 수정 반영 |

백로그를 직접 여는 일이 없어야 정상이다.

예약 실행 자체는 `_posts` 이동·커밋·푸시를 하지 않는다. `_posts` 이동과
커밋은 명시적 발행 승인 뒤에만 수행하고, 푸시는 별도 요청이 있을 때만
수행한다.

## 7. 하지 않는 것

- 사례·판단·감정을 지어서 채우기 (즉시 중단 사유)
- 답변 재촉
- 하루 2건 이상 선별
- 사망 항목 자동 부활
- 승인 없는 발행·커밋
- 외부 SEO 씨앗의 무근거 승격
